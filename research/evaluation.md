# FORGE — Evaluation & Deployment Brief

> Scope: How FORGE will measure whether a small model *actually* codes, and how it will run/train within ₹0 constraints. All benchmark sizes and EvalPlus multipliers below are from primary papers/repos. Throughput and size figures that are not directly measured are labelled **[estimate — derived]** with method shown. No pass@1 scores are claimed for FORGE — none exist yet.

**Last updated:** 2026-10-24 · **Status:** Pre-implementation design, to be frozen before first training run

---

## 0. Principles

1. **Functional correctness only.** A sample counts as solved iff it passes *all* hidden tests in a sandboxed process. Syntax validity, BLEU, or explanation quality never substitute.
2. **Greedy pass@1 is the headline.** Sampling-based pass@k is secondary — FORGE targets single-attempt usefulness on a phone.
3. **Final test set is write-once.** Dev sets may be iterated on; the final split is evaluated ≤ once per major milestone and never used for checkpoint selection.
4. **Every number ships with its conditions:** model hash, decoding (temp/top-p/max tokens), prompt template, `n`, hardware, quantisation, and timeout.
5. **Report failures, not just averages:** breakdown by error class (syntax / import / timeout / assertion) is mandatory.

## 1. Proposed Benchmark Suite

### 1.1 What the standard benchmarks actually are

| Benchmark | Origin | Size | Structure | Tests / problem | Notes |
|---|---|---|---|---|---|
| **HumanEval** | Chen et al., *Evaluating Large Language Models Trained on Code*, 2021 | **164** hand-written Python problems | Function signature + docstring → complete function body | ~7.7 avg in original release (EvalPlus paper reports 9.6 incl. prompt tests; counts vary by counting method) | Standalone functions only; stdlib only. Small *n* → wide CIs (see §1.4). |
| **MBPP** | Austin et al., *Program Synthesis with Large Language Models*, 2021 | **974** crowd-sourced problems; **427 sanitized** subset hand-verified; standard test split **257** (sanitized test), full splits commonly 374 train / 90 val / 500 test | Natural-language description (1 sentence typical) + canonical solution | **3** assert statements | Entry-level: numeric / list / string manipulation dominate (≈58% maths, 43% list in authors' 100-sample audit). | **FORGE-Heldout (custom)** | FORGE, to be authored *before* training data freeze | **120** problems (target) | Same format as HumanEval (signature + docstring + hidden tests, ≥10 tests each) | ≥10 | See §1.3. This is the only set FORGE fully controls for contamination. |

### 1.2 pass@k — definition (do not improvise)

From Chen et al. 2021, unbiased estimator used by HumanEval / EvalPlus:

For each problem, generate `n` samples (`n ≥ k`), let `c` = number passing all tests:

```
pass@k := E_problems [ 1 − C(n−c, k) / C(n, k) ]
```

- **pass@1 with `n=1`, greedy decoding (T=0)** = fraction of problems solved on the single deterministic attempt. This is FORGE's primary metric — cheapest, reproducible, matches phone use.
- **pass@1 estimated from sampling** (`n=20`, T=0.8, top-p 0.95) = `c/n` averaged — report separately as `pass@1 (sampled)`, never conflated with greedy.
- **pass@10** (`n=20`, T=0.8) is diagnostic only: a large pass@10 − pass@1 gap means the model *can* solve but unreliably — points to decoding / self-consistency work, not more pretraining.
- EvalPlus protocol in the paper: 200 samples × temps {0.2,0.4,0.6,0.8} + greedy. FORGE cannot afford that on free GPUs — see reduced protocol §1.3.

### 1.3 FORGE evaluation protocol (frozen for v1)

**Execution harness:** Fork of EvalPlus execution (process isolation per sample, `reliability_guard`, I/O swallowed, temp dir). Hard limits per sample: **10 s wall-clock, 512 MB RAM, no network, no filesystem outside temp dir**. One timeout = fail, not retry.

| Tier | Set | n problems | Decoding | When run | Purpose |
|---|---|---|---|---|---|
| **Dev (iterable)** | MBPP+ val slice + HumanEval+ *seen as dev only in phase 0* | 90 (MBPP val) | greedy, max 256 new tokens | Every checkpoint | Checkpoint selection, ablations |
| **Primary report** | **HumanEval+** (164) + **MBPP+** (378) | **542 total** | greedy pass@1 (n=1) **and** sampled pass@1 / pass@10 (n=20, T=0.8, top-p 0.95) | Per milestone | Comparable to literature; report base **and** `+` scores side-by-side (the delta = fragility) |
| **Protected final** | **FORGE-Heldout** (120) + HumanEval+ re-run | 120 + 164 | greedy only | Once per major version, hash-logged | Generalisation claim. Never in training data, never tuned on. |
| **Micro / regression** | FORGE-Syntax (50 fill-in / completion prompts, authored with heldout) | 50 | greedy | Every commit in CI (CPU, tiny model only) | Catches tokenizer / template breakage cheaply |

**Additionally tracked per run (all tiers):**

| Metric | Definition | Why |
|---|---|---|
| Syntax success % | Parses with `ast.parse` / compiles | Separates "doesn't know Python" from "wrong algorithm" |
| Execution success % | Runs without exception (may still fail asserts) | Second stage of funnel |
| Test pass rate (partial) | Mean fraction of hidden tests passed per problem | Softer signal when pass@1 ≈ 0 for tiny models |
| Duplicate / template rate | % generations that are near-duplicates (MinHash Jaccard >0.8) of another generation or a training doc | Detects memorised-template collapse |
| Contamination flags | See §1.5 | Validity gate — flagged problems reported both included and excluded |
| Context-truncation rate | % prompts + generation hitting max length | Catches silent eval bugs |

**Prompting (frozen):** HumanEval: zero-shot, raw completion (signature + docstring as given, no chat template for base models). MBPP+: 3-shot with the 3 canonical EvalPlus few-shot examples, held fixed across all models/baselines. Any change = new eval version (`forge-eval-v2`), old results not comparable.

### 1.4 Sample counts & uncertainty — read this before celebrating a 2-point gain

- HumanEval alone (n=164): a pass@1 of 10% has Wilson 95% CI ≈ **±4.6 pp**; 30% → ±7.0 pp. Differences < ~7 pp on HumanEval alone are **not evidence**.
- Combined primary (n=542): 10% → ±2.5 pp; 30% → ±3.9 pp. Still coarse. FORGE must report **Wilson intervals** or bootstrap CIs (1,000 resamples over problems) with every score.
- FORGE-Heldout (n=120) is for direction + contamination control, not fine ranking.
- Never report pass@k without `n`, temperature, and seed count. Sampled metrics: 3 seeds, report mean ± sd across seeds.

### 1.5 Contamination — the central validity threat for code

HumanEval / MBPP solutions have circulated on GitHub, in notebooks, and in synthetic datasets since 2021. Established findings:

- N-gram decontamination is the standard first wall: GPT-3 used 13-gram overlap; PaLM flagged examples with ≥70% 8-gram overlap; Qwen2.5-Coder reports **10-gram** collisions against HumanEval. StarCoder / RedPajama audits found **~8–18% of HumanEval** overlapping common pretraining corpora (per Yang et al. 2023 decontamination study, as summarised in contamination reviews).
- N-gram methods **miss paraphrased / rephrased contamination entirely** (F1 ≈ 0 on rephrased samples in Deng et al. 2023) — a model fine-tuned on rephrased HumanEval can reach near-GPT-4 benchmark scores undetected by n-grams.
- Therefore FORGE does **all** of:
  1. **10-gram + 13-gram overlap** of every training document against all benchmark prompts + canonical solutions (normalised: lowercased, whitespace/punctuation stripped, identifiers preserved). Any hit → document dropped, hit logged with benchmark ID.
  2. **MinHash near-duplicate** (Jaccard ≥0.7 on token 5-gram shingles) against benchmark solutions — catches renamed-variable copies.
  3. **Source quarantine:** any repo/file whose path or URL contains `humaneval`, `mbpp`, `evalplus`, or known solution-mirror names is excluded wholesale, regardless of per-file match.
  4. **Canary + audit:** FORGE-Heldout problems are never published before final eval; their hashes are committed (not the text) at data-freeze time so later leakage is provable.
  5. **Reporting:** if a baseline (e.g. an open-weight model) has unknown training data, its HumanEval+ score is labelled `contamination: unknown` and FORGE-Heldout is the fair comparison.

### 1.6 Systems metrics (reported alongside every correctness score)

| Metric | How measured | Report as |
|---|---|---|
| Parameter count | `sum(p.numel())`, non-embedding and total separately | M params |
| Checkpoint size | File bytes on disk for FP16, Q8_0, Q4_K_M | MB per quant |
| Peak RAM (inference) | `llama.cpp` RSS high-water (`/usr/bin/time -v` / Android `dumpsys meminfo`) at ctx 1024, batch 1 | MB |
| Latency | Time to first token + inter-token, median of 20 runs, warm | ms/token |
| Throughput | Decode tokens/sec, batch 1, ctx 512, greedy, phone CPU (4 threads) and GPU eval host separately | tok/s (device named) |
| Training cost | GPU type, wall-hours, tokens seen, est. FLOPs = 6·N·D | GPU-h + tokens |
| Energy proxy (phone) | Battery drain over 100 generations *[optional, noisy]* | % / 100 gens |

## 2. Deployment Path — Android / Termux

### 2.1 Runtime decision

| Runtime | Format | Verdict for FORGE |
|---|---|---|
| **llama.cpp + GGUF** ✅ Primary | Single `.gguf` file (weights + tokenizer + metadata), pure C/C++, ARM NEON kernels, mmap loading, MIT | **Chosen.** Builds in Termux (`cmake` + `clang`), no Python runtime needed at inference, widest quant support (2–8 bit K-quants), streaming CLI (`llama-cli`) and server mode. Demonstrated running GGUF models in Termux on commodity Android (e.g. Llama 3.2 3B Q4 on Snapdragon 750G / 12 GB device in Yadav & Bhargavi 2025, ICT4SD). |
| ONNX Runtime Mobile | `.onnx` + external data, NNAPI / QNN execution providers | Viable fallback, *not* primary: graph export for autoregressive decoding + KV-cache handling is more fragile for custom architectures; INT8 dynamic quant is easy but 4-bit LLM support is via GenAI extension and less mature than GGUF K-quants. Better suited to encoder / Whisper-style models. Keep as Plan B if FORGE adopts a non-Llama-compatible architecture that GGUF conversion cannot express. |
| ExecuTorch / LiteRT-LM | `.pte` / `.litertlm` | Promising (NPU access) but toolchain-heavy, device-specific, and overkill at 100–500M scale where CPU NEON already saturates. Revisit only if profiling shows CPU is the blocker. |
| Pure PyTorch / Transformers on phone | `.bin` / safetensors | **Rejected** for deployment: Python + torch install in Termux is multi-GB, slow, and battery-hostile. Acceptable only as a correctness reference. |

**Implication for architecture (binding):** FORGE's architecture must be **GGUF-convertible** — i.e. expressible with ops llama.cpp supports (standard decoder: RMSNorm, RoPE, SwiGLU, GQA are all supported) and convertible via `convert_hf_to_gguf.py`. Exotic attention / recurrence needs a llama.cpp fork — treat that as a major cost and justify explicitly.

### 2.2 Quantisation — sizes and trade-offs

GGUF K-quants use mixed precision (sensitive tensors get more bits). Effective bits/weight and sizes **[derived: params × bits/8, + ~5–10% metadata/KV overhead in practice]**:

| Quant | Bits/weight (eff.) | 125M | 350M | 500M | 7B (reference) | Quality expectation |
|---|---|---|---|---|---|---|
| FP16 (reference) | 16.0 | 250 MB | 700 MB | 1,000 MB | ~13.5 GB | Baseline |
| **Q8_0** | ~8.5 | ~133 MB | ~372 MB | ~531 MB | ~6.7–8.5 GB | Near-lossless (llama.cpp PPL Δ ≈ +0.0004 on reference models); use as **eval reference quant** |
| **Q6_K** | ~6.6 | ~103 MB | ~289 MB | ~413 MB | ~5.5 GB | Excellent; preferred if RAM allows |
| **Q5_K_M** | ~5.7 | ~89 MB | ~249 MB | ~356 MB | ~4.8 GB | Very good, minimal loss (<1% on typical benchmarks in community evals) |
| **Q4_K_M** ✅ default ship | ~4.8 | **~75 MB** | **~210 MB** | **~300 MB** | ~4.1 GB | Good — llama.cpp's recommended default; 1–3% quality loss typical on large models. **Caution for small models:** recent work (e.g. *Not All Bits Are Equal*, 2025) finds 4-bit is *memory-suboptimal for reasoning in small models* (0.6–1.7B) — the accuracy lost outweighs memory saved vs 8-bit. FORGE must A/B this (see below), not assume it. |
| Q3_K_M | ~3.4 | ~53 MB | ~149 MB | ~213 MB | ~3.3 GB | Noticeable loss; only if storage-constrained |
| Q2_K | ~2.5 | ~39 MB | ~109 MB | ~156 MB | ~2.7 GB | Poor; do not ship for code — code is precision-sensitive (exact tokens matter) |

**FORGE quantisation protocol (mandatory ablation):**
For each release candidate, evaluate HumanEval+ greedy pass@1 at **FP16 → Q8_0 → Q5_K_M → Q4_K_M** on identical prompts. Ship the smallest quant whose pass@1 drop vs FP16 is **≤1.5 pp** (within CI overlap). Expectation to test, not assume: at 125–350M, Q8_0 or Q5_K_M may be the real ship quant, with Q4_K_M winning only on file size. Also measure the quantisation *benefit*: Q4 weights read ~3.3× fewer bytes per token than FP16, so decode (memory-bandwidth-bound at batch 1) is typically **faster** on phone CPUs despite dequantisation overhead — verify on device, don't trust desktop numbers.

**KV cache warning:** weights are not the whole RAM story. KV cache ≈ `2 × layers × kv_heads × head_dim × ctx × bytes`. For a 350M model (e.g. 24 layers, 8 KV heads, dim 64, ctx 2048, FP16 cache) ≈ 200 MB — comparable to Q4 weights. FORGE should: default ctx **1024** on phone, offer llama.cpp KV-cache quantisation (`-ctk q8_0 -ctv q8_0`) as an option, and report peak RAM at the *shipped* ctx.

### 2.3 What actually runs on a phone

Rule of thumb: model file should be **≤ ~30% of device RAM** to leave room for OS, KV cache, and Termux.

| Device tier (typical India-market Android) | RAM | FORGE fit |
|---|---|---|
| Budget (4 GB) | 4 GB | 125M Q4_K_M (~75 MB) / Q8_0 (~133 MB) — comfortable. 350M Q4 also fits. Expect **[estimate]** ~8–20 tok/s decode for 125M, ~4–10 tok/s for 350M on mid-range SoC CPU (4 threads, NEON) — *must be measured on target device; community reports for ~1B Q4 models on phones cluster around 6–10 tok/s* |
| Mid-range (6–8 GB) ✅ design target | 6–8 GB | Entire FORGE range (≤500M, any quant ≤Q8) comfortable; 500M Q8 (~531 MB) still <10% RAM |
| Flagship (12 GB+) | 12 GB+ | Headroom for retrieval index + execution sandbox alongside model (see Baseline C) |

FORGE's size advantage is real: unlike a 7B Q4 (~4.1 GB, needs 8 GB+ phone, ~4–6 GB runtime RAM), a 125–500M FORGE model is **not RAM-constrained at all** — the constraints shift to *capability*, thermals on sustained generation, and battery. Keep generations short (≤256 tokens default) and stream output.

**Termux deployment steps (to be scripted as `deploy/termux_install.sh`):**
```bash
pkg install git cmake clang python
git clone https://github.com/ggml-org/llama.cpp && cd llama.cpp
cmake -B build -DLLAMA_CURL=OFF && cmake --build build -j4
# convert (on GPU host / Kaggle, not phone):
python convert_hf_to_gguf.py /path/to/forge-hf --outfile forge-f16.gguf
./build/bin/llama-quantize forge-f16.gguf forge-q4km.gguf Q4_K_M
# run (on phone):
./build/bin/llama-cli -m forge-q4km.gguf -p "<prompt>" -n 256 -t 4 --temp 0
```
Ollama in Termux is an alternative wrapper over the same GGUF/llama.cpp stack — optional, not required.

## 3. Free-GPU Training Feasibility

> **Verify at run time.** Free tiers change without notice. Figures below reflect widely reported limits as of late 2025 / 2026 community + provider docs — treat as planning values, re-check the Kaggle/Colab quota page on the day.

### 3.1 What "free" actually gives you

| Platform | GPU | VRAM | Session limit | Quota | Storage | Reliability notes |
|---|---|---|---|---|---|---|
| **Kaggle Notebooks** ✅ primary | P100 (16 GB) *or* T4 ×1/×2 (16 GB each) — assignment varies | 16 GB (P100) / 16 GB per T4 | **9–12 h** per session (docs/community vary; plan for 9 h) | **~30 GPU-h / week** (shown in account settings; floats with demand) | 20 GB persistent (datasets + notebook outputs) | Most predictable free option. No credit card. PyTorch + HF preinstalled. Datasets mount read-only — ideal for frozen corpora. |
| **Google Colab Free** | Usually T4 (16 GB); occasionally L4 / other; **not guaranteed** | ~16 GB | **12 h max**, ~90 min idle disconnect | **No published quota** — dynamic, "heavily restricted", can be zero in peak periods | Ephemeral (~100 GB scratch, wiped on reset); Drive mount for checkpoints | Good for prototyping / eval bursts, bad as the sole training host. Never run an un-checkpointed job here. |
| Lightning AI Free / HF ZeroGPU / SageMaker Studio Lab | T4-class / shared | varies | 4 h-class sessions, minutes/day (ZeroGPU) | ~15–22 T4-h/month (Lightning, reported) | varies | Studio Lab closed to new users (2026). ZeroGPU is demo inference only (5 min/day) — **not training**. List as opportunistic only. |

**Planning assumption for FORGE:** Kaggle is the training host (30 h/week budget), Colab is overflow/eval. Total realistic budget: **~120 GPU-h / month** if both are used diligently, less if quotas tighten. Design every run to fit this.

### 3.2 Throughput estimates [estimate — derived from 6ND]

Training FLOPs/token ≈ **6·N** (2N forward + 4N backward, Kaplan/Chinchilla approximation; attention term small at ctx ≤1024). Effective throughput = `peak_FLOPS × MFU / (6N)`. Assumed MFU **25–35%** — realistic for a small model, short context, vanilla PyTorch + AdamW on a single GPU (large-model 50% MFU does *not* apply here; kernel launch + dataloader overheads dominate at 100–500M).

| Model | T4 (65 TFLOPS FP16 peak) theoretical @25–35% MFU | P100 (~18.7 TFLOPS FP16, no tensor cores — effectively lower MFU) | **Planning number** (×0.6 haircut for dataloader, checkpointing, eval pauses, notebook overhead) |
|---|---|---|---|
| 125M | 21.7k–30.3k tok/s | 6.2k–8.7k tok/s | **T4: ~10k–15k tok/s · P100: ~4k–6k tok/s** |
| 250M | 10.8k–15.2k tok/s | 3.1k–4.4k tok/s | T4: ~6k–9k tok/s · P100: ~2k–3k tok/s |
| 350M | 7.7k–10.8k tok/s | 2.2k–3.1k tok/s | T4: ~4.5k–6.5k tok/s · P100: ~1.5k–2k tok/s |
| 500M | 5.4k–7.6k tok/s | 1.6k–2.2k tok/s | T4: ~3k–4.5k tok/s · P100: ~1k–1.5k tok/s |

**Time for 1B tokens (planning numbers, T4 / P100):** 125M ≈ **19–28 h / 46–69 h** · 350M ≈ **43–62 h / 139–185 h** · 500M ≈ **62–93 h / 185–278 h**.

**What this means — be honest:**
- Chinchilla-optimal for 350M is ~7B tokens (20 tok/param). At Kaggle-only 30 h/week on T4, that's **~10–14 weeks** of perfect quota use. On P100 assignment, 3× longer. **A fully Chinchilla-optimal from-scratch run is not a v1 plan.**
- Feasible v1 targets: **125M on 1–2B tokens** (overtrained relative to size is fine — inference-optimal, like Llama-style overtraining) ≈ 2–4 Kaggle-weeks; **350M on 1B tokens** (undertrained, a scaling probe) ≈ 2 Kaggle-weeks. Both fit the milestone structure.
- Getting T4 ×2 on Kaggle + DDP roughly doubles throughput *if* the notebook offers it — verify per session, never assume.
- Sequence packing, `torch.compile`, FlashAttention (T4 supports FA2 via SDPA), and fused AdamW are the cheapest throughput wins — each must be A/B'd for actual tok/s, not assumed.

### 3.3 Memory — will it fit in 16 GB?

Mixed-precision AdamW footprint ≈ weights BF16 (2 B) + FP32 master (4 B) + Adam m,v FP32 (8 B) + gradients BF16/FP32 (2–4 B) ≈ **16–18 B/param** before activations:

| Model | Optimiser + weights + grads | Activations (batch 16 × 1024 ctx, grad checkpointing ON) | Total (est.) | Fits 16 GB? |
|---|---|---|---|---|
| 125M | ~2.0–2.3 GB | ~1–2 GB | ~3–4.5 GB | ✅ Easily; can raise batch / disable checkpointing for speed |
| 350M | ~5.6–6.3 GB | ~2–3 GB | ~8–9.5 GB | ✅ |
| 500M | ~8.0–9.0 GB | ~2.4 GB | ~10.5–12 GB | ✅ with grad checkpointing; tight without |

All FORGE sizes fit a single T4/P100. No model parallelism needed. If OOM: gradient accumulation (micro-batch 8 × accum 4) before any architecture change.

### 3.4 Checkpointing & interruption recovery (non-negotiable on free tiers)

Sessions *will* die (quota, idle timeout, pre-emption). Design for it:

- **Checkpoint every 30 min of wall time or 500 steps, whichever first** — full state: model, optimiser, scheduler, RNG, dataloader position (or epoch + shuffle seed + sample offset), config hash, git SHA, tokens-seen counter.
- Checkpoint size: model-only FP16 = 0.25 GB (125M) – 1.0 GB (500M); **full resumable** (with Adam) ≈ 6–9× that (~1.5 GB / ~6 GB). Keep **last 2 full + last 1 model-only** on persistent storage; rotate, never overwrite the only known-good.
- **Write pattern:** write to local scratch → fsync → atomic rename → copy to Kaggle Dataset / Drive / GitHub Release (whichever is the run's designated store). A half-written checkpoint on a dying session is the #1 avoidable loss.
- **Resume test is part of acceptance:** every training script must pass kill-at-random-point → resume → loss curve continuous (no spike > agreed threshold) before a real run starts.
- Log `tokens_seen`, `wall_elapsed`, `gpu_type` per checkpoint so cross-session / cross-GPU continuations are auditable. LR schedule must be a function of tokens-seen, not wall time or session count.

## 4. Baselines — what every FORGE result is compared against

Every experiment reports against **all applicable baselines on the identical eval protocol (§1.3)**. No baseline = no claim.

### B0 — Trivial / floor baselines (always run, ~zero cost)
| Baseline | Definition | What it proves |
|---|---|---|
| **Empty / signature-only** | Return the prompt function with `pass` / `return None` body | Floor for partial-test-pass rate; catches eval harness bugs (if this scores >0 on pass@1, the harness is broken) |
| **Most-common-template** | Emit the single most frequent training-set solution pattern (e.g. sorted-list / loop-accumulate template fitted per prompt keyword) | Measures how far dumb template matching gets on MBPP-style tasks — FORGE must beat this clearly or it has learned templates, not coding |
| **Copy-retrieval (no model)** | BM25 / embedding retrieval of nearest training problem, return its canonical solution verbatim | Floor for Baseline C; isolates retrieval value from generation value |

### B1 — Tiny transformer trained from scratch (the control)
Decoder-only transformer, **~30–50M params**, same tokenizer, same data, same token budget *per run* as the FORGE candidate it controls for, trained with the vanilla recipe (no packing tricks, no curriculum, no execution filtering). Purpose: any FORGE "innovation" must beat B1 at equal tokens, or the innovation is not doing anything. This is also the CI regression model (trains in <1 Kaggle session).

### B2 — Open-weight reference (external yardstick, not a competitor)
One small permissively-licensed pretrained code/general model that fits the eval host, evaluated **zero-shot under the identical harness** — e.g. a 0.5B–1.5B-class open-weight coder (exact checkpoint + licence + hash pinned at eval-freeze time; candidates in this class include Qwen2.5-Coder-0.5B / SmolLM2-360M-class models — **selection and licence verification is an explicit pre-eval task, do not assume**). Labelled `contamination: unknown` (§1.5). Purpose: calibrates whether FORGE's absolute numbers are in a sane range and what adaptation (Approach B in the main plan) could achieve. FORGE is *not* required to beat B2 in v1 — it is required to *report the gap honestly*.

### B3 — FORGE model-only (the candidate)
The current FORGE architecture, greedy decoding, no retrieval, no execution feedback, no self-repair. **This is the number that goes in the headline.** All system tricks are reported as deltas *over B3*, never merged into it.

### B4 — FORGE + system (retrieval / execution / decomposition)
Same weights as B3, plus one mechanism at a time, then combined:
- **B4a Retrieval:** top-3 similar solved problems (from a decontaminated, index-frozen corpus — *never* from benchmark sets) prepended as few-shot context.
- **B4b Execution feedback:** generate → run visible tests (MBPP's 3 public asserts / docstring examples only — never hidden tests) → on failure, one repair attempt with traceback in context. Report pass@1 *and* pass@1-after-1-repair separately, plus mean generations/problem (cost).
- **B4c Decomposition:** model first emits a plan / sub-function signatures, then implements. Same total token budget cap as B3 for fairness.

**Fair-comparison rules:** B4 variants get the same base weights, same max total tokens/problem (counting retries and retrieved context), and their extra latency / RAM (index size) is reported in the systems table. If B4 ≫ B3, that is a *system* result — valuable, but it does not retroactively make the *model* good, and the report must say so.

### Baseline acceptance thresholds (v1, pre-registered)
- B3 must beat **B0-template** and **B0-retrieval** on primary pass@1 by a margin exceeding CI overlap.
- B3 must beat **B1** at equal tokens for any claimed training improvement to be accepted.
- Quantised ship candidate must satisfy §2.2 (≤1.5 pp drop vs FP16).
- Any result failing contamination audit (§1.5) is **invalid regardless of score**.
